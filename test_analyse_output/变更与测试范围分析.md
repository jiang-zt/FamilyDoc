## 7. 测试范围

### 7.1 必测（P0）

1. **空库增量**：先按既有流程建 `app_user` / `chat_record` / `chat_metric` 并插入样例行，再执行 `shared-chat-schema.sql`。断言：三张新表存在；旧表行数与结构不变。
2. **幂等再执行**：同一库连续执行两次脚本，第二次不得失败（`IF NOT EXISTS`）。
3. **唯一约束**  
   - `uk_chat_conversation_user`：同一 `user_id` 第二行失败。  
   - `uk_chat_generation_client`：同一 `(user_id, client_request_id)` 失败。  
   - `uk_chat_shared_message_seq`：同一 `(conversation_id, seq)` 失败。
4. **可空列**：`chat_conversation.active_request_id`、`chat_generation.error_code` 允许 NULL。
5. **默认值**：仅插入 `chat_conversation(id, user_id)` 时 `version=0`、`next_seq=0`、`created_at` 非空。
6. **不自动建表**：启动 head 已提交的 Spring 应用（不手工执行本 SQL）后，库中不应因应用启动而出现这三张表（与文件注释一致）。

### 7.2 建议测（P1）

1. **索引存在性**：`idx_chat_generation_lease`、`idx_chat_shared_message_request`、上述 UNIQUE。
2. **类型边界**：`question` TEXT、`content` MEDIUMTEXT 可写入超过 64KB 的内容；`DATETIME(3)` 可写入毫秒。
3. **与旧 `chat_record` 并存**：新旧表可同时插入，互不影响。
4. **新库顺序**：注释要求「账号/指标初始化后执行」。测：只跑本文件、不跑 `schema.sql` 也能建三张表；但回放账号授权范围是 `*.*` 时后续应用是否仍缺旧表（运维文档风险，不是应用 bug）。
5. **回放库缺口**：head 的 `init_db.py` 未加载本文件。若后续提交会把共享会话接到回放，需补：`init_db` 拼接本 SQL + `test_init_db.py` 断言三表存在。本区间可不改代码，但应记为**已知环境缺口**。

## 8. 风险与审查点

| 风险 | 级别 | 说明 |
| --- | --- | --- |
| 无外键 | 中 | `conversation_id` / `request_id` 可指向不存在的行；应用层需自行保证，本区间无应用代码。 |
| `IF NOT EXISTS` 不演进结构 | 中 | 若后续改列，旧库不会被这份脚本修复。 |
| 状态/角色无 CHECK | 低 | `status`/`role` 任意字符串可入库。 |
| `chat_generation.conversation_id` 无单列索引 | 低 | 按会话查生成历史可能全表扫（本区间无查询代码）。 |
| 脚本位置 | 低 | 放在 `src/main/resources` 但明确不自动执行，容易被误认为 Boot 会加载。 |
| 运维遗漏 | 高（对后续功能） | 注释写了手动执行；head 回放初始化未纳入。表不存在时后续 Java 才会失败。 |
| 与未提交代码不同步 | 信息 | 工作区已有用法（租约 300s、`FOR UPDATE`、消息 seq 成对写入）。那些行为**不在本次测试合同内**。 |
