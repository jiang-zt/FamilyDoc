1. Spring Boot 核心

Q1: Spring Boot 自动装配原理是什么？

Spring Boot 自动装配的核心是 @SpringBootApplication 注解，它包含三个关键注解：

  1. @SpringBootConfiguration - 标识这是一个配置类
  2. @ComponentScan - 扫描当前包及子包下的 Bean
  3. @EnableAutoConfiguration - 开启自动装配

自动装配流程：

启动 → 读取 spring.factories → 加载所有 AutoConfiguration 类 
     → 根据 @Conditional 注解判断是否生效 → 注册 Bean 到 IOC 容器

关键注解：

  • @ConditionalOnClass - 当类路径存在某类时生效
  • @ConditionalOnMissingBean - 当容器中没有某 Bean 时生效
  • @ConditionalOnProperty - 当配置文件有某属性时生效

本项目中的体现：

  • spring-boot-starter-web 自动配置了 Tomcat、DispatcherServlet
  • mybatis-plus-boot-starter 自动配置了 SqlSessionFactory、Mapper 扫描
面试加分点：Spring Boot 2.7+ 使用 META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports 替代了 spring.factories，性能更好。
Q2: Spring Boot 启动流程是怎样的？
SpringApplication.run(Application.class, args);

启动五步：

  1. 初始化 SpringApplication 对象 - 推断应用类型、加载 Initializer 和 Listener
  2. 准备环境 - 创建 Environment、加载配置文件
  3. 创建容器 - 创建 ApplicationContext
  4. 刷新容器 - refresh()：扫描 Bean、注册 BeanDefinition、实例化单例 Bean
  5. 运行完成 - 调用 ApplicationRunners、输出启动日志

本项目启动类：

@SpringBootApplication
@MapperScan("com.itzixi.mapper")
public class Application {
    public static void main(String[] args) {
        SpringApplication.run(Application.class, args);
    }
}

@MapperScan 作用：指定 MyBatis Mapper 接口所在包，自动扫描并注册 Mapper 代理对象到 Spring 容器。

Q3: Spring Bean 的生命周期？

完整生命周期（12 步）：

1. 实例化 Bean → 2. 属性赋值 → 3. Aware 接口回调 → 4. BeanPostProcessor.before()
→ 5. InitializingBean.afterPropertiesSet() / @PostConstruct → 6. 自定义 init-method
→ 7. Bean 就绪 → 8. 业务调用 → 9. DisposableBean.destroy() / @PreDestroy
→ 10. 自定义 destroy-method → 11. BeanPostProcessor.after() → 12. Bean 销毁

  • @Resource 依赖注入在属性赋值阶段完成
  • SSEServer 的静态初始化在类加载时完成
面试加分点：BeanPostProcessor 是 Spring 的核心扩展点，AOP、@Async、@Transactional 都通过它实现。

2. Spring AI 与 LLM 集成

Q5: Spring AI 是什么？如何集成 Ollama？

Spring AI 是 Spring 官方推出的 AI 框架，提供统一的 API 接入各种 LLM 提供商（OpenAI、Anthropic、Ollama 等）。

核心组件：

  • ChatClient - 对话客户端
  • ChatModel - 底层模型接口
  • Prompt - 提示词封装
  • ChatResponse - 响应封装

Ollama 集成步骤：

  1. 添加依赖 
    <dependency>
    <groupId>io.springboot.ai</groupId>
    <artifactId>spring-ai-ollama</artifactId>
    <version>1.0.3</version>
</dependency>
  2. 配置文件 
    spring:
  ai:
    ollama:
      base-url: http://127.0.0.1:11434
      chat:
        model: deepseek-coder:latest
  3. 注入使用 
    @Resource
private OllamaChatClient ollamaChatClient;
String response = ollamaChatClient.call("你好");

Ollama 是什么：本地运行 LLM 的工具，支持 DeepSeek、Llama、Mistral 等开源模型，API 兼容 OpenAI 格式，无需 API 密钥。

面试加分点：Spring AI 的 ChatMemory 支持上下文记忆，通过 MessageChatMemoryAdvisor 实现多轮对话。生产环境建议使用 Redis 存储对话历史。

3. SSE 流式输出

Q8: SSE (Server-Sent Events) 原理是什么？

SSE 是单向 HTTP 长连接，服务器主动推送数据给客户端。

核心 API：

SseEmitter sseEmitter = new SseEmitter(0L);  // 0 = 永不过期
sseEmitter.send(SseEmitter.event()
    .id(userId).name("message").data(content)
);

工作流程：

  1. 客户端发起 GET 请求，设置 Accept: text/event-stream
  2. 服务器创建 SseEmitter，保持连接
  3. 服务器调用 send() 推送数据
  4. 客户端通过 EventSource.onmessage 接收
  5. 连接关闭时调用 complete()

本项目 SSE 实现：

public static SseEmitter connect(String userId) {
    SseEmitter sseEmitter = new SseEmitter(0L);
    sseEmitter.onCompletion(completionCallback(userId));
    sseEmitter.onError(errorCallback(userId));
    sseEmitter.onTimeout(timeoutCallback(userId));
    sseClients.put(userId, sseEmitter);
    onlineCounts.getAndIncrement();
    return sseEmitter;
}
Q9: SSE vs WebSocket 有什么区别？
对比项SSEWebSocket
协议HTTP (text/event-stream)ws:// / wss://
通信方向单向（服务器→客户端）双向
浏览器支持原生 EventSource API原生 WebSocket API
复杂度简单，基于 HTTP复杂，需要握手协议
适用场景通知、日志、流式输出实时聊天、游戏、协作

本项目选择 SSE 的原因：AI 流式输出是单向推送，基于 HTTP 无需额外协议，实现简单，Spring 原生支持。

面试加分点：大厂高并发场景下，SSE 和 WebSocket 都需要考虑：连接数限制、心跳检测、断线重连、负载均衡 sticky session。
Q10: SSE 连接如何管理？线程安全问题？

本项目连接管理：

private static Map<String, SseEmitter> sseClients = new ConcurrentHashMap<>();
private static AtomicInteger onlineCounts = new AtomicInteger(0);

线程安全分析：

  1. ConcurrentHashMap - 线程安全的 Map，基于 CAS + synchronized，读操作无锁
  2. AtomicInteger - 原子整数，基于 CAS，无锁实现

潜在问题：

// 问题：检查 + 操作不是原子操作
if (sseClients.containsKey(userId)) {
    sseEmitter.send(...);  // 可能此时连接已被移除
}
// 解决：使用 computeIfPresent 或加锁
面试加分点：生产环境建议使用 ConcurrentHashMap.compute() 方法保证原子性。
Q11: SSE 超时问题如何处理？

SseEmitter 超时配置：

SseEmitter sseEmitter = new SseEmitter(0L);  // 0 = 永不过期（默认 30 秒）

超时回调：

sseEmitter.onTimeout(() -> {
    log.info("SSE 连接超时，用户 ID: {}", userId);
    removeConnection(userId);
});

生产环境建议：

  1. 设置合理超时时间（如 5 分钟）
  2. 实现心跳机制（定期发送空消息）
  3. 客户端实现重连逻辑
  4. 服务端清理僵尸连接

Q13: MyBatis 的 #{} 和 ${} 有什么区别？
对比项#{} ${}

Q14: 数据库 ID 生成策略有哪些？本项目用的是什么？

常见 ID 生成策略：

策略说明优点缺点
自增 IDAUTO_INCREMENT简单分布式不安全
UUIDUUID.randomUUID()全局唯一无序，索引效率低
雪花算法Snowflake有序，全局唯一依赖时钟

本项目配置：

mybatis-plus:
  global-config:
    db-config:
      id-type: assign_id  # 雪花算法

雪花算法结构（64 bit）：

  • 1 bit: 符号位（0）
  • 41 bit: 时间戳（毫秒级，约 69 年）
  • 10 bit: 机器 ID（5 位数据中心 + 5 位机器 ID）
  • 12 bit: 序列号（同一毫秒内的递增序号）
面试加分点：分布式场景下，雪花算法的时钟回拨问题需要处理。大厂通常使用美团 Leaf、百度 UidGenerator 等成熟方案。
Q15: 数据库索引优化原则？

索引创建原则：

  1. 高频查询字段 - WHERE、JOIN、ORDER BY 字段
  2. 区分度高 - 基数大的字段（如 ID、时间）
  3. 复合索引 - 最左前缀匹配原则
  4. 避免过度索引 - 写操作多的表谨慎

本项目索引建议：

CREATE INDEX idx_family_member ON chat_record(family_member);
CREATE INDEX idx_member_time ON chat_record(family_member, chat_time DESC);

最左前缀原则：

-- 复合索引 (a, b, c)
WHERE a = 1              -- 命中
WHERE a = 1 AND b = 2    -- 命中
WHERE b = 2              -- 不命中
WHERE c = 3              -- 不命中

5. 并发编程与线程安全

Q16: ConcurrentHashMap 原理是什么？

JDK8 实现：

结构：数组 + 链表 + 红黑树
├─ Node[] table: 哈希桶数组
├─ 链表：hash 冲突时链式存储
└─ 红黑树：链表长度 > 8 时树化

线程安全机制：

  1. CAS + synchronized - 头节点插入用 CAS，链表/树操作用 synchronized 锁头节点
  2. 细粒度锁 - 锁粒度是桶（bin），不是整个 Map
  3. volatile 变量 - 保证可见性

本项目使用：

private static Map<String, SseEmitter> sseClients = new ConcurrentHashMap<>();
面试加分点：JDK7 使用分段锁（Segment），JDK8 改为 CAS + synchronized，性能提升 3-5 倍。
Q17: AtomicInteger 原理是什么？

AtomicInteger 基于 CAS（Compare-And-Swap）：

public final int getAndIncrement() {
    return U.getAndAddInt(this, VALUE, 1);
}

CPU 级指令：

lock; cmpxchg  // 锁定总线，比较交换

本项目使用：

private static AtomicInteger onlineCounts = new AtomicInteger(0);
onlineCounts.getAndIncrement();  // +1
onlineCounts.getAndDecrement();  // -1

vs synchronized：

对比项AtomicIntegersynchronized
实现CAS（乐观锁）监视器锁（悲观锁）
性能高（无锁）低（锁竞争）
适用简单原子操作复杂同步逻辑
Q18: 什么是 volatile？有什么用？

volatile 两大特性：

  1. 可见性 - 一个线程修改 volatile 变量，其他线程立即可见
  2. 有序性 - 禁止指令重排序

volatile 不保证原子性：

volatile int count = 0;
count++;  // 不是原子操作（读 - 改 - 写）
// 解决：使用 AtomicInteger
AtomicInteger count = new AtomicInteger(0);
count.getAndIncrement();  // 原子操作
面试加分点：JMM（Java 内存模型）通过 happens-before 规则定义内存可见性。volatile 写 happens-before 后续 volatile 读。
Q19: 线程池核心参数有哪些？如何配置？

ThreadPoolExecutor 7 个参数：

new ThreadPoolExecutor(
    int corePoolSize,      // 核心线程数
    int maximumPoolSize,   // 最大线程数
    long keepAliveTime,    // 非核心线程存活时间
    TimeUnit unit,         // 时间单位
    BlockingQueue<Runnable> workQueue,  // 工作队列
    ThreadFactory threadFactory,        // 线程工厂
    RejectedExecutionHandler handler    // 拒绝策略
)

工作流程：

1. 提交任务 → 核心线程未满 → 创建核心线程执行
2. 核心线程已满 → 加入工作队列
3. 队列已满 → 创建非核心线程（直到最大线程数）
4. 达到最大线程数 → 执行拒绝策略

拒绝策略：

  • AbortPolicy - 抛出 RejectedExecutionException（默认）
  • CallerRunsPolicy - 调用者线程执行
  • DiscardPolicy - 丢弃任务
  • DiscardOldestPolicy - 丢弃最老任务

6. 系统设计与架构

Q20: 如何设计一个高可用的 AI 对话系统？

架构分层：

┌─────────────────────────────────────────┐
│           负载均衡层 (Nginx/SLB)         │
├─────────────────────────────────────────┤
│           应用层 (Spring Boot 集群)      │
├─────────────────────────────────────────┤

├─────────────────────────────────────────┤

高可用措施：

  1. 负载均衡 - Nginx 反向代理、健康检查、会话粘性
  2. 限流熔断 - Sentinel 限流、降级策略
  3. 监控告警 - Prometheus + Grafana
面试加分点：大厂生产环境使用 Service Mesh（如 Istio）管理流量，AI 服务通常部署在 GPU 集群，通过 Kubernetes 自动伸缩。
Q21: SSE 连接在集群环境下如何处理？

问题：SSE 连接绑定到单个 JVM，集群环境下用户可能连接到不同节点。

解决方案：

  1. 会话粘性（Sticky Session） - Nginx ip_hash 配置，简单但负载不均
  2. Redis 发布/订阅 - 所有节点订阅 Redis 频道，高可用但实现复杂
  3. WebSocket + 消息队列 - 使用 RabbitMQ/Kafka 广播消息
面试加分点：大厂通常使用 Redis Pub/Sub 或消息队列，配合 Kubernetes 的亲和性调度保证连接稳定性。
Q22: 如何设计数据库表结构支持千万级数据？

分库分表策略：

  1. 水平分表（按用户） - 按 family_member 哈希分 100 个表
  2. 垂直分表（按时间） - 按月分表
  3. 读写分离 - 主库写、从库读
  4. 冷热分离 - 最近 3 个月热数据，历史数据归档

分区表示例：

CREATE TABLE chat_record (...) 
PARTITION BY RANGE (YEAR(chat_time)) (
    PARTITION p2024 VALUES LESS THAN (2025),
    PARTITION p2025 VALUES LESS THAN (2026),
    PARTITION p2026 VALUES LESS THAN (2027)
);

7. 性能优化

Q23: 如何优化 AI 对话的响应时间？

优化策略：

  1. 模型选择 - 使用小模型、量化模型（INT8/INT4）
  2. 流式输出 - 首 token 时间 < 100ms
  3. 缓存热门问答 - Redis 缓存 FAQ 
    String cachedAnswer = redis.opsForValue().get("faq:" + md5(question));
  4. 异步处理 - 聊天记录保存异步化 @Async
  5. 连接池优化 - HikariCP 配置
面试加分点：大厂使用模型蒸馏 + 量化 + 批处理优化推理性能，首 token 时间可压到 50ms 以内。
Q24: 如何优化数据库查询性能？

优化手段：

  1. 索引优化 - 复合索引、覆盖索引
  2. 分页优化 - 避免深分页，使用游标分页 
    -- 深分页问题
SELECT * FROM table LIMIT 10000, 20;
-- 优化：游标分页
SELECT * FROM table WHERE id < ? ORDER BY id DESC LIMIT 20;
  3. 批量操作 - 批量插入
  4. 慢查询日志 - 开启慢查询监控
Q25: 如何减少内存占用？

内存优化策略：

  1. SSE 连接清理 - 及时清理失效连接
  2. 流式处理 - 逐 token 处理，不占用大量内存
  3. JVM 调优 
    -Xms512m -Xmx1g
-XX:+UseG1GC
-XX:MaxGCPauseMillis=200

8. 生产问题排查

Q26: 线上 CPU 100% 如何排查？

排查步骤：

# 1. 找到高 CPU 的进程
top -c
# 2. 找到高 CPU 的线程
top -H -p <pid>
# 3. 转换线程 ID 为十六进制
printf "%x\n" <tid>
# 4. 导出线程栈
jstack <pid> > thread_dump.txt
# 5. 搜索十六进制线程 ID
grep -A 20 <hex_tid> thread_dump.txt

常见原因：死循环、频繁 GC、序列化/反序列化、正则表达式回溯、锁竞争

Q27: 线上 OOM 如何排查？

排查步骤：

# 1. 查看堆内存
jmap -heap <pid>
# 2. 导出堆 dump
jmap -dump:format=b,file=heap.hprof <pid>
# 3. 分析 dump 文件
MAT (Memory Analyzer Tool)

常见原因：内存泄漏、大对象、缓存无限制、ThreadLocal 未清理

本项目可能的问题：SSE 连接未清理，内存泄漏

// 解决：确保回调清理
sseEmitter.onCompletion(() -> removeConnection(userId));
Q28: 线上接口响应慢如何排查？

排查步骤：

  1. 查看应用监控（Prometheus/Grafana）
  2. 查看慢查询日志
  3. 查看线程栈 jstack
  4. 使用 Arthas 追踪 trace 命令

常见原因：数据库慢查询、AI 模型响应慢、锁竞争、Full GC、网络延迟
